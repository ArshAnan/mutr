CPU layout
  Guest has 8 vCPUs, numbered 0-7.
  The largest server configuration is 4 mutr worker threads, or Redis io-threads 4.
  Those need a fixed set of cores, and the client must keep the same cores on every run.
  Giving the client the leftover cores when the server uses only 1 thread would make the client faster on the small-server runs, so the split does not move.
  Server process: taskset -c 0-3
  memtier: taskset -c 4-7
  The two sets do not overlap.
  mutr --pin is off. Workers are not pinned inside 0-3. The acceptor thread shares 0-3 with the workers.
  --threads 4 is 4 workers plus that acceptor, so 5 threads on 4 cores.
  --threads 8 is not run: it would need cores 0-7 and would share cores with memtier.
  memtier threads: -t 4, one thread per client core.
  Total connections are -t times -c:
    8 connections:  -t 4 -c 2
    32 connections: -t 4 -c 8
    128 connections: -t 4 -c 32
    512 connections: -t 4 -c 128

Measurement conditions that are easy to misread
  memtier --test-time and --requests are mutually exclusive in this build.
  Timed runs pass only --test-time. With that set, this memtier does not
  apply the default of 10000 requests (memtier_benchmark.cpp: if both are
  unset, requests becomes 10000). A smoke run's JSON Runtime Total duration
  was 30000 MILLISECONDS.
  memtier peak_cpu_utilization_pct is an aggregate across its threads. A
  4-thread client reported a peak above 100 while mpstat idle on cores 4-7
  stayed near 60. Client-bound means mpstat %idle under 5 on a core in 4-7,
  or one memtier thread cores_used >= 0.95. The aggregate peak is stored
  and is not the saturation test.
  A harness check, not a result: one GET run preloaded set_count 1000000
  and recorded misses/sec 0.00. One 512-connection SET against each server
  recorded connection errors 0. Listen backlog in the server is unchanged.
